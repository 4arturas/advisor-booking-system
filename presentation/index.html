Advisor Booking System

Java 25 Spring Boot 4.1 PostgreSQL Redis RabbitMQ Microsoft Graph API
Chosen style: Modular monolith with clear internal modules. Keep it simple now, split later if demand or team size grows.

What this deck answers

1. Solution Overview

Architecture style

  • Modular monolith with domain modules for booking, calendar, and notification.
  • Best fit for the scope and team size implied by the assignment.
  • Simple deployment, low operational overhead, easy to maintain.
  • Clear boundaries make future extraction into microservices possible.

Key technologies

  • Spring Boot REST API for web and mobile channels.
  • PostgreSQL for durable booking storage.
  • Redis for short-lived slot reservation / caching.
  • RabbitMQ for asynchronous email processing.
  • Microsoft Graph API for Outlook calendar and email integration.

Expected Java components

BookingController
REST endpoints for availability, booking, cancel, and lookup
BookingService
Core booking orchestration and transaction boundary
CalendarService
Graph API calls for availability and event creation
NotificationService
Confirmation / cancellation email handling
BookingRepository
Persistent booking storage in PostgreSQL
Advisor / BookingSlot entities
Domain model for advisors, slots, and bookings

2. Architecture Diagram

flowchart LR
  Website[Website] --> API[Backend API\nSpring Boot]
  Mobile[Mobile App] --> API
  API --> DB[(PostgreSQL)]
  API --> Cache[(Redis)]
  API --> MQ[(RabbitMQ)]
  API --> Graph[Microsoft Graph API]
  Graph --> Calendar[Exchange Online Calendar]
  Graph --> Email[Email / Outlook]
  MQ --> EmailSvc[Notification handling]
  EmailSvc --> Graph
The API remains the single entry point. Web and mobile use the same booking contract, which keeps business rules consistent across channels.

Step-by-Step Booking Flow

1.
Customer submits a booking request from website or mobile app.
2.
BookingController validates the request and passes it to BookingService.
3.
BookingService checks current slot availability and starts a database transaction.
4.
The chosen slot is locked and re-checked inside PostgreSQL so two requests cannot win at the same time.
5.
CalendarService creates the event in Exchange / Outlook through Microsoft Graph API.
6.
The booking is stored in PostgreSQL and the slot is marked as no longer available.
7.
A confirmation event is published for email handling; the customer receives the confirmed booking response.

3. Handling Race Conditions

How duplicates are prevented

  • Database transaction keeps booking creation atomic.
  • Pessimistic locking prevents concurrent requests from claiming the same slot.
  • Unique constraint on advisor + slot time is the final safety net.
  • Redis reservation can optionally hide the slot from other channels for a short time.

User experience

  • If Customer A wins, the slot is confirmed immediately.
  • If Customer B arrives milliseconds later, the API returns a clean "slot unavailable" response.
  • The UI should refresh the available slots list and prompt the user to choose another time.
Consistency mechanism: database isolation + row lock + unique constraint. That combination is stronger than a cache-only approach.

4. Error Handling

Scenario Customer experience Logging Retries
Calendar service unavailable Booking is rejected with a friendly "calendar temporarily unavailable" message. Log the Graph API error, advisor ID, and request correlation ID. Yes, retry a few times with backoff; do not confirm the booking without calendar success.
Database unavailable Show a maintenance / try again later message. Log as critical infrastructure failure and trigger health alerts. No. Do not continue when persistence is unavailable.
Confirmation email fails The booking still remains confirmed; email is retried asynchronously. Log warning with booking ID and message details. Yes, use queue retry + dead-letter queue for manual follow-up.

5. Scalability and Monitoring

Scale target

500,000 bookings / month

That is roughly 700 bookings per hour. The load is manageable for a modular monolith with a single PostgreSQL backend and horizontal API scaling.

  • Add more API instances behind a load balancer.
  • Keep booking rules in one place to avoid channel drift.
  • Use Redis for hot availability reads and PostgreSQL for the source of truth.

Monitoring in production

  • Metrics: Prometheus + Grafana
  • Logs: centralized structured logs
  • Tracing: request correlation ID per booking
  • Health: actuator health checks for DB, queue, and external API availability
Key operational metrics: booking success rate, average booking latency, calendar API latency, email delivery success, and database pool saturation.

Summary

  • A modular monolith is the simplest solution that still meets the business needs.
  • PostgreSQL is the source of truth; Redis and RabbitMQ improve responsiveness and resilience.
  • Race conditions are handled at the database level, not by UI timing.
  • Calendar and email are integrated through Microsoft Graph API, keeping the Microsoft 365 ecosystem intact.
  • The design can scale to the requested volume and is easy to evolve later.
